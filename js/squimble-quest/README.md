# Squimble Quest

Top-down RPG in p5.js (v1.11, global mode) and plain JavaScript, played at `squimble-quest.html`. No build step, modules or npm: the page loads every file here with `<script>` tags in a set order, sharing globals.

**Scope:** quests and combat across worlds with their own themes: forests, underwater, volcanoes and fire worlds, deserts, wastelands and post-apocalypse, snow, swamps, caves, space and alien planets. A world is a set of maps, and each map gets its look and feel (fog, colour, weather, background sound) from an atmosphere (see **Atmospheres** below), so a new world is mostly new tiles, objects, enemies and an atmosphere, not new code.

## Keep the notes true

This README and the code comments are the only notes. When you change something:

- **Changed how something works?** Update the comments beside it, and this README or the maps README where they describe it.
- **Added a file?** Add it to the list atop `sketch.js` and the `<script>` tags in `squimble-quest.html` (order matters).
- **Changed the map editor or map format?** Update the [maps README](../../assets/squimble-quest/maps/README.md) (the map-building guide).
- **Made a non-obvious choice** (a why, or something tried that failed)? Comment it where it matters, or note it here if it's game-wide.
- **Finished an [idea](#ideas-for-later) or [known issue](#known-issues-and-loose-ends)?** Remove it. **Found a problem or left something half done?** Add it.
- **Found a stale note?** Fix or delete it. A wrong note is worse than none.

## Start here

- **`sketch.js`**: the game loop; its header lists every file. Read it first.
- **[maps README](../../assets/squimble-quest/maps/README.md)**: map editor guide and map file format.
- **Catalogue files** (`tiles.js`, `objects.js`, `enemies.js`, `npcs.js`, `weapons.js`, `items.js`, `sound.js`) each open with a "how to make one" guide. Tiles, weapons, items and sounds are data files the editor can change and export (see Tiles, Inventory and Sound below).

**Running:** maps load with `fetch`, so serve it locally (see "Running the game locally" in the maps README), e.g. `py -m http.server 8765` from the portfolio root, then `http://localhost:8765/squimble-quest.html`. From `file://` it falls back to a blank stand-in map.

**Pause:** **Esc** in the game opens the pause menu (`pausemenu.js`): volumes, then the Sound, Screen and Assist settings below, and changing keys, kept in the browser (`sq-settings`). Not a save: game progress still resets on reload.

**Accessibility:** every setting is a `GAME_SETTINGS` line (config.js, saying where it's read) plus a `SETTING_ROWS` row (pausemenu.js: tab, label, tip, and tick, % slider or picker), which gives it a field, loading (type and range checked), saving and right click to reset. A new one is those two lines and the code that reads it.
  - Seeing: screen shake, damage numbers, a colour blind filter (`colourblind.js`: a daltonizing SVG colour matrix as the canvas's CSS filter, so it sits over every shader and the UI), Flashes (dims lightning and the hurt glow, for photosensitivity) and Crosshair size.
  - Hearing: Captions (`Captions`, access.js) get every sound through `Sound.onPlay` and show its words with an arrow to it, merging repeats (footsteps), skipping your own, npc speech (already on screen), previews and anything too far to hear. Words come from `SOUND_CAPTIONS`, else the sound's name. Mono (`Sound.mono`) centres every pan. `tests/access-check.js` checks the captions.
  - Assist: Auto pause opens the menu when the window blurs or the tab hides (`PauseMenu.away`). Nothing here changes how the game plays (speed, damage), since that would fight the balance and multiplayer.
  - Not built yet, in rough order: text size (dialogue, messages, captions), a hold-free roll and interact, off-screen enemy arrows, and shapes or patterns next to colours (rarity) for players who see no colour.

**Dev mode:** **`** or **Ctrl + D**. Then **H** opens the dev menu (pick what the info panel and map show, click tools, see every key), **M** next map, **T** teleport to mouse, **- = 0** zoom out/in/reset, **G** toggle tile grid, **P** toggle enemy AI routes, **[ ]** previous/next shader. **B** opens the map editor, with or without dev mode.

**Who can use them:** dev mode and the editor are powers a role gives (`ROLES` and `PLAYER_ROLE` in config.js, checked with `player.can('dev')` / `can('build')`): a `developer` gets both, a `builder` just the editor, a `player` neither. Each has one check where it starts (`Debug.toggle()`, `Editor.open()`), so nothing else needs to know. It's `developer` while making the game; **set `PLAYER_ROLE` to `'player'` before shipping** and both are gone. That only hides them, since the code still ships: with multiplayer the server hands out roles and checks them again before accepting a builder's changes (the `multiplayer:` note on `PLAYER_ROLE`).

## How the code is written

- **Keep it simple.** Build the smallest thing that works. No features, settings or layers "for later".
- **Keep multiplayer possible** (only a maybe, see [Ideas](#ideas-for-later); don't build for it). Prefer the multiplayer-safe way when it costs nothing:
  - only `sketch.js` reads keyboard and mouse; everything else gets `{ move, aim, attack }` controls or is told what happened
  - AIs and triggers find players with `nearestPlayer(world, from)` (character.js) from the `world.players` list, never assuming one player
  - per-player state lives on the player (e.g. `player.stepTile` for step warps and step sound blocks), not in a shared global
  - game state is plain numbers, strings and lists, no p5 colours or images (tiles keep `fill`/`img` apart from their settings; `MeleeSwing` makes its colour in `draw()`)
  - gameplay never pauses the world: talking to an NPC doesn't (the dev-only editor does)
  - randomness goes through one shared function, not scattered `Math.random()`
- **In-game UI** (`ui.js`, `button.js`, `textfield.js`), never `prompt()`/`alert()`.
- **The game is 960 x 540 game px** (`GAME_W`/`GAME_H`, config.js), however big it's shown (see **Screen size** under [How it fits together](#how-it-fits-together)). Place UI from `GAME_W`/`GAME_H` (the edges or the middle) rather than fixed numbers like `x: 900`, and keep world distances (sight, reach) in world px or tiles.
- **Comment style:** write them like notes to yourself: lowercase, British spelling (`colour`), plain words in normal sentences rather than clipped fragments. Say *why*, or what isn't obvious from the code; don't restate it. Use "I" for decisions and things that were tried ("I tried X first, but..."). Plain keyboard characters only: "to" or `->` rather than arrows, `x` rather than `×`, "+/-" rather than `±`. Explain jargon. Constants and object properties get a short note on purpose or units unless the name says it all. Name the file of another file's global, e.g. `// worldMap is the game's (sketch.js)`.
- **Data files** (`datafiles.js`, user guide `assets/squimble-quest/README.md`): every kind of data is a folder in `assets/squimble-quest/` (`DATA_KINDS`: tiles, sounds, voices, items, objects, enemies, npcs, parts, particles, atmospheres, maps) with one `<name>.json` per thing (its non-default settings, no name inside) and an `index.json` listing names in load/palette order. Each owning file calls `DataFiles.register(kind, { define, loaded?, names?, toData? })`; `setup()` loads every kind, then maps. Export buttons call `DataFiles.export(kinds, extras)`, which downloads only files whose `toData()` text differs from load (or the last export) and says which names to add to or remove from `index.json` (`tellWhere()`). `tests/data-check.js` checks every index against its folder. Behaviour stays in code and files name it: an enemy's `ai` is an `ENEMY_AIS` name and `onDeath` an `ENEMY_DEATHS` name. A weapon lives inside its owner's file (`makeWeapon()`), so an item and its weapon never download as two `sword.json`s.
- **Catalogue pattern:** `defineObject/Enemy/Npc/Item(name, settings)` all go through `defineType()` / `withDefaults()` (utils.js), which fills defaults and warns on settings missing from them (usually typos), so a genuinely new setting needs a default. The editor picks new entries up automatically. Tiles go through `setTile()`, filled from `TILE_DEFAULTS` (unknown keys dropped). Files are written back as non-default settings only (`typeToData()` in utils.js, 2 space JSON from `DataFiles.text()`).

## How it fits together

- **Maps** (`maps.js`, `mapfile.js`, `tilemap.js`):
  - One JSON file per map in `assets/squimble-quest/maps/`, listed in `maps/index.json`. Format at the top of `mapfile.js`.
  - `MAPS[name]` builds a map fresh. Always add maps with `addMap()`, which also drops any visited copy.
  - `getMap(name)` builds on first need and keeps it in `VISITED_MAPS`, so editor changes last until reload. `loadMap(name, warpName)` (sketch.js) goes to a map through it.
- **Warps** (`warps.js`, whose header has the full spec): tiles that move the player to another map or elsewhere on this one (doors, caves, manholes, trapdoors, passages, teleporters). A same-map warp is a teleport: only the player moves and the camera glides (another map snaps it).
  - Warps only move the player. Other things you press E on (signs, levers) are their own kind, a line in `INTERACTABLES` (interact.js) like chests and sound blocks.
  - Each map's `warps`: `{ name, col, row, to, toWarp, activate, enemies }`. Every warp is both exit and arrival, so a house needs two, each leading to the other.
  - Links go by **name**: `to` a map name, `toWarp` a warp name there (`''` = that map's spawn). Moving a warp is safe; renaming breaks links to it.
  - `activate`: `step` (on stepping onto it) or `interact` (E within `WARP_REACH`, over a tile, so it works from the tile in front).
  - **Enemies can follow** with `enemies: true`: on use, each enemy chasing the player that `canFollow()` allows gets `enemy.following = { warp, time }` (straight-line walk time, plus its kind's `doorOpenTime` for E warps). `canFollow()` is the one place that decides: the warp's `enemies`, the enemy's `followsThroughWarps` (its kind's, or its spawn's `follows`), and E warps count as doors, so `doorOpenTime: null` kinds get left behind there. New rules (locked doors, keys, size) go in `canFollow()`, and a door animation would start in `comeOut()`. Same map: it really walks (`Enemy.followThroughWarp()`). Other map: maps the player isn't on stand still, so it moves into `Warps.followers` and `Warps.update()` counts down. Either way `Warps.comeOut()` places it on the arrival tile when due, even if a wall blocked it. Enemies never use warps on their own.
  - **Arriving on a step warp doesn't bounce you back:** step warps fire only when the player's tile *changes* onto them, and `Warps.arrived()` marks the landing tile as stepped on (`loadMap` and `Player.respawn` call it).
  - Warps track the player's tile themselves (`feetTile()`), not `player.tileCol`/`tileRow`, which lag a frame after a mid-frame death and respawn; that used to send players back out the warp they arrived by.
  - `warpProblem(warp)` explains a broken target. Used when warping (`showMessage()`, hud.js), for red editor markers, and by `checkAllWarps()` (console warnings once maps load).
  - **Warp graph** (`warpgraph.js`, whose header explains the layout): **Show links** in a warp's settings draws every linked warp as a family tree, and **Map > World map** the same with a box per map; clicking a box goes there. It draws only what's on screen and `sketch.js` skips the world under it, so 100+ warps stay smooth (`node-test`'s `square` is the test).
  - Warps are separate from tiles and objects (those can't store a target). To make one *look* like a door, put an object on its tile. An `interact` warp works under a solid object since E reaches from the next tile.
- **TileMap** (`tilemap.js`):
  - Holds `tiles` (names, `null` empty), `objects`, `enemySpawns`, `npcSpawns` (each `{ type, col, row }`), `warps`, `spawn` (world pixels) and `characters`.
  - Empty and off-map tiles are solid.
  - `resize()` and `usedArea()` handle resizing. `SPAWN_KINDS` maps enemies/NPCs to their lists and file keys.
  - Tiles draw on screen pixels with every edge rounded and shared by neighbours, so no faint grid at any zoom (see above `drawTiles()`).
- **Tiles** (`tiles.js`, `tileeditor.js`):
  - One file per tile in `assets/squimble-quest/tiles/`: colour, dual grid, texture, `variants` and `frames` (more pictures, normal tiles only: `tileImageAt()` picks a variant by position with `tileHash()`, or the frame by time, every `frameTime` s; frames win), `oldNames` (names it had, so maps still saying one get it: `resolveTileName()` in `mapFromData()`, `getMap()` via `TileMap.updateTileNames()`, undo and paste), behaviour (`solid`, `speed`, `damagePerSecond`, `damagePerStep`, `healPerSecond`, `slippery`, `pushDirection`, `pushSpeed`) and `blendsWith` (which dual grid tiles round onto it). `index.json` order = editor bar order = dual grid layer order.
  - The tile files load before the maps (`sketch.js`), since map loading checks tiles exist, and loading waits for textures so nothing flashes plain colour. A missing/broken file only warns; with no tiles there's just `blank`, for the stand-in map.
  - `setTile(settings, picture)` adds or changes a tile, and is the only way into `TILE_TYPES`. Its `DataFiles.register('tile')` turns them back into files; exporting unchanged downloads nothing.
  - Textures: `assets/squimble-quest/tiles/normal/` (pictures, including variants and frames) and `dual-grid/` (tilesets). `texture` is the file name; `texturePath()` adds the folder from `dualGrid`. Variant and frame pictures load once each through `TILE_PICTURES` (file name → promise of the image), which the tile editor also fills with chosen pictures.
  - **Tile editor** (`tileeditor.js`): a tabbed `FormBox` with a side column (`TilePreview`, **Choose picture**). **Look** is built by hand; other tabs come from `TILE_BEHAVIOURS` (one line per setting naming its tab), so a new setting or tab is one line. Tabs over `TILE_EDITOR_ROWS` rows continue in a numbered tab. Editing a placed tile previews live (`onUpdate` calls `setTile()` whenever the box would save); closing unsaved restores a copy taken on open (`onCancel`). **Save** calls `setTile()` with the chosen picture, so it works before the picture is in the folder. **Export** downloads the files of new or changed tiles plus any picture chosen since load (`TileEditor.newPictures`, variants and frames too), since the game only loads textures from its folders. The **Name** row renames on Save (`renameTile()`), and **Delete tile** asks for a replacement (`deleteTile()`): both swap the name in every built map, add to the kept tile's `oldNames`, fix other tiles' `blendsWith` and the editor's picks; Export then lists the old file to delete. `PictureListField` is the variants/frames row.
  - Tiles are data, so no per-tile code (the old `onEnter`/`onStand`); damage and speed cover it. New behaviour (e.g. a teleporting tile) = a `TILE_DEFAULTS` setting, handled in `walk()` or `checkTile()` (`character.js`), plus a `TILE_BEHAVIOURS` line.
- **Dual grid tiles** (`dualgrid.js`, on via `dualGrid`): ground like grass that blends into neighbours with rounded edges. Maps and the editor just see `'grass'`; only drawing changes (the editor badges them, `drawDualBadge()`). `drawTiles()` draws normal tiles, then `drawDualCorner()` at every corner of a second grid offset half a tile, each piece chosen by which of the four meeting tiles are grass (`DUAL_TILESET_LAYOUT`). See-through edges show a normal tile from that corner beneath. A tile whose `blendsWith` excludes a dual grid tile counts as covered in that piece's bits, so the piece runs straight to it, and that quarter isn't drawn (`cut`), leaving the tile visible. Where two dual grid tiles meet, the later in `tiles/index.json` goes on top (`layer`), so list lowest first (dirt before grass); new tiles append, so they're on top. Tilesets are cut into 16 pictures whenever a tile gets one (`useTexture()` in `tiles.js`, `cutDualTileset()`), since drawing part of a big image can bleed a line of the neighbouring piece at some zooms. `dualTilesetProblem()` explains a bad tileset to the tile editor.
- **Maps remember their characters.** Leaving a map stores its live `enemies` and `npcs` on `map.characters`; returning restores them, so defeated stay gone, hurt stay hurt, everyone stays put until reload.
  - The spawn lists (`enemySpawns`, `npcSpawns`) are the design and never change on death, so Export saves all of them.
  - `spawnCharacters()` makes everyone fresh from the spawn lists: on a map's first visit and whenever the editor opens, closes or changes characters (opening the editor is a quick enemy reset).
  - This replaced a `defeated` set of spawns, and fixed hurt enemies healing when you left and returned.
- **Characters** (`character.js`):
  - Player, enemies and NPCs all take `{ move, aim, attack }`: from keyboard/mouse for the player, from `ai(entity, world, dt)` otherwise.
  - Tile settings apply to everyone: `speed`, `slippery` and push in `walk()`, damage and healing in `checkTile()`. `velocity` only persists on slippery tiles; elsewhere it's replaced each frame.
  - **Enemy AI:** each spawn can pick one of `ENEMY_AIS` (enemies.js), saved as its `ai`, else its kind's; read `Enemy.ai`, not `settings.ai`. Every ai finds who to chase with `sensePlayer()` (sight, hearing, alerting allies, memory; the "senses" notes in enemies.js), and the pathfinders plan A* routes round walls and harm and round each other. **The header of `pathfinding.js` is the full guide** (pieces, costs, tuning, known limits, extending it). Dev mode draws each plan, `tests/pathfinding-check.js` checks the choices, and the `ai-test` map is for watching them.
  - **Dying** (placeholder): `Character.hurt()` calls `die()`, which for the player just sets `dead`. They disappear (or leave `PLAYER.deathImage`), `deathscreen.js` darkens the screen with **Respawn** (or E), and `Player.respawn()` brings them back at the current map's `spawn` with a fresh start. While dead they aren't in `world.players`, so enemies lose interest, and they can't move, use things or pick things up (`updatePlaying()` in sketch.js). The header of `deathscreen.js` lists it all; where you respawn is undecided ([Known issues](#known-issues-and-loose-ends)).
- **Looks** (`looks.js`, whose header is the full guide): what a character looks like, for the character creator. A look is plain data, `{ parts: { slot: partName }, colours: { group: { name: hex } } }`; parts are files in `parts/`, recoloured and stacked into one cached picture (`lookImage()`), and `withLook(settings, look)` hands it to `Character` as its `img`, so nothing else knows looks exist. NPC kinds and spawns take a `look`. **Pictures are drawn at their own size** with their bottom middle on the feet, separate from the hitbox, so art can change size without code changes.
- **Weapons** (`weapons.js`, whose header lists every setting and where it acts): a weapon's `attack` names a `WEAPON_ATTACKS` entry, which has its editor `label`, whether it's `ranged` and a `start()` that makes the attack: `swing` (a `MeleeSwing`, kept on its owner while it lasts), `jab` (a `Jab`, the spear: a `MeleeSwing` whose `hitTargets()` pushes a point straight out to its `reach` and stops at the first body it touches) or `shoot` (an `Arrow`, like the bow). Ask `isRanged(weapon)`, never `attack === 'shoot'`, so a new ranged attack works everywhere. Swings and jabs never hit through walls: `MeleeSwing.clearTo()` needs a `clearLine()` from the owner's feet to the target's, and a jab's point stops at the first wall along the floor, the same walls that stop arrows (not water). Arrows outlive the attack and their owner, so they live in sketch.js's `arrows` list (passed to characters as `world.arrows`), forgotten on changing map and in `spawnCharacters()`. An arrow is top down like particles (a floor spot plus a height), hits the first of its owner's `targets()` its tip touches, stops at tiles that block sight, and drops onto the floor at its `reach`. The arrow is a drawn line until there's a sprite (`ponytail:` note on `Arrow`), and its shadow is a temporary dash squashed up and down (`drawArrowShadow()`, its own section in weapons.js to delete when there's a shadow system).
  - **How hits feel:** every hit, swing or arrow, goes through `hitWith()` (weapons.js): particles, knockback (`Character.pushTowards()`, a `pushVelocity` on top of walking that slows at `COMBAT.pushFade` and stops at walls and characters), `stagger` (can't walk or attack), a hit stop (`Character.freeze()`: hitter and hit stand still for the weapon's `hitStop`; arrows don't freeze the shooter) and screen shake (`Camera.shake(shake, shakeTime)` on the attacker's or target's `Character.camera`, which only this computer's `player` has, so it's multiplayer-safe; a bigger shake takes over a smaller one, and the jolt moves the drawing, not the camera). Every one of these is a weapon setting, so an enemy's weapon decides how hard the player gets shaken. What's hit can take more or less knockback and stagger (an enemy's `knockbackTaken` and `staggerTaken`; the dummy takes no knockback), and an enemy deals its `damageScale` and attacks again its `attackSpeed` times quicker (`wieldedHit()`). Damage goes last, so a killing blow's knockback doesn't follow the player to their respawn. Knockback and recoil take over walking (`pushTowards(..., takeOver)`, `pushedHard()`) until they slow to `COMBAT.pushLockEnd`, so walking against them can't cut them short. A swing's `windup` holds it raised before it sweeps (`MeleeSwing.windingUp`, drawn as a brightening blade), lunges when the sweep starts, and is cancelled by a stagger; `carrySpeed` slows whoever holds the weapon (the axe). Attacks can `lunge` the attacker forwards (the axe, the grunt) and a landed swing can `recoil` them back (the sword's stab), and an attack click is buffered for `COMBAT.attackBuffer` so it fires as soon as the weapon's ready, even during a hit stop. All per character, so the world never pauses.
  - **Extras on every hit** (`hitWith()`, settings in `COMBAT` in config.js): a squash (`Character.squash`, drawn only), a damage number (`DamageNumbers` in weapons.js, updated, drawn on top and cleared on changing map by sketch.js), and the weapon's `hitSound` / `killSound` through `weaponSound()` (each weapon has its own sounds and volume, pitch, random pitch and weight, the editor's Sound tab; `Sound.play()`'s `rate`, `volume` and `minVolume` options do it per play). Hits this computer's player lands are at least the weapon's `hitHeard` loud however far away (the bow). The player also plays `PLAYER.hurtSound`. A bow with a `chargeTime` plays its `drawSound` from the start of the draw (`Character.drawVoice`) and `stopDrawing()` cuts it off when it shoots or loses the shot; anything that drops a draw should call `stopDrawing()` rather than setting `charge` to null. A kill adds `COMBAT.killShake` and holds a melee swinger for `COMBAT.killHitStop` (`MeleeSwing.strike()`). A character with `hitInvincible` (the player, `PLAYER` in config.js) can't be hit again for that long (`Character.invincible`, read by `hittable()`, drawn as a blink, plus `drawHurtFlash()` in hud.js). Health bars show lost health as a trail that drains (`Character.trailHealth`). The weapon editor's preview characters have `inPreview`, so they make no numbers, and sounds only while the Sound tab is open (`audible`).
  - **Dodge roll** (Shift, `ROLL` in config.js, `Character.canRoll()`, `startRoll()`, `rollOn()`): only while wearing an item with `roll: true` (the quick charm, an accessory), whatever's in hand. It goes the way you're walking or else the way you're facing, slowed by sand and `carrySpeed` like walking. No walking or attacking while rolling. It can't be hit for the first `ROLL.invincible` seconds (`Character.hittable()`, which swings and arrows check instead of `dead`), and `bodyBox()` is only `ROLL.height` as tall for the whole roll. A stagger ends it, and a press mid-swing is buffered like attacks.
  - **Combos:** a weapon's `combo` is a list of hits, each only the settings that differ from the weapon; `comboHit()` merges them. `Character.attack()` counts `comboStep` and starts over after `comboWindow` past the cooldown or on changing weapon. The sword is three hits (two quick slashes, then a narrow long stab that throws them back and recoils you), the axe two (the second a wide heavy swing). 
  - **Charged shots:** a shooting weapon with a `chargeTime` (the bow) draws while attack is held and shoots when let go (`Character.updateCharge()`). `chargePower()` goes from `minPower` to 1 over `chargeTime` and scales damage, reach, arrow speed and knockback (`poweredHit()`), you walk at `chargeSlow` speed while drawing, and a stagger loses the shot, so camping at range costs something. The player sends `controls.charge` (mouse held); ais leave it out and keep attacking, which lets go at full draw. `drawChargeLine()` shows how far it would fly now, dotted until fully drawn, for enemy archers too.
  - **Weapon editor** (`weaponeditor.js`): the Weapon, Hit, Feel and Sound tabs `Editor.editItem()` adds after an item's Item tab, also used alone for an enemy kind's own weapon. Every `HIT_SETTINGS` line is a slider, kept per combo hit (`WEAPON_WIDE_SETTINGS` on the Weapon tab, or the Sound tab with the `WEAPON_SOUNDS` pickers if their `tab` says so, are the whole weapon's) (the Hit picker on Hit and Feel; the Combo picker adds hits by copying the last). Save writes hit 1 as the weapon's own settings and each hit's differences as `combo` (`hitsToSettings()`), so a combo hit's own `colour` or `attack` written by hand is dropped on saving from the editor. `WeaponPreview` loops the whole combo with two real `Character`s on `PREVIEW_FLOOR` (no walls, no particles) and its own `Camera` for the shake, and makes its sounds (full volume) only while the Sound tab is open. Enemy kinds' own weapons end the Weapons tab as "grunt's weapon" with a badge (`enemyWeaponNames()`, `drawEnemyWeaponArt()`); they're never picked, any click opens them. The tab's Export saves `enemy` files too (`toData` in enemies.js, which leaves out settings that are the default, like the grunt's `width`).
  - **Enemies' weapons:** an enemy uses its kind's `weapon` (the grunt's claws) unless its spawn `holds` an item (picked in the editor, saved in the map; `null` is empty hands), through `Enemy.currentWeapon()`. Every ai decides whether it can attack with `canAttack()` (enemies.js): a swing reaches `attackRange` or the weapon's reach, whichever's further; a shot reaches `ENEMY_SHOT_RANGE` of the bow's reach; both need a clear line, so nothing swings at a wall. While it can shoot it stands still (`isShooting()`, in `chasePlayer` and `huntAlongPath()`), so archers keep their distance and walk closer when a wall's in the way. Held items are drawn small in the hand (`heldItem()`, `drawCharacter()`), for the player too.
- **Inventory** (`inventory.js`):
  - One row of slots: the first `HOTBAR_SIZE` are the hotbar (the only pickable ones), the next `BAG_SIZE` the bag, then the player's `EQUIPMENT_SLOTS` (head, body, legs, feet, three accessories). `add()` fills the first empty carrying slot, hotbar first, never equipment. An equipment slot only takes items whose `wear` (items.js, a `WEAR_PLACES` key) is its `wear`, which `swap()` checks (`fits()`).
  - **E or I** opens `InventoryScreen` (E only with no NPC, E warp or chest in reach, so I always works). The game runs on but the player stands still and nothing's in reach. Equipment is down both sides of a `CharacterPreview` of the player (it turns to the mouse and wears what's in the slots), the bag and hotbar on the right. Drag onto a slot to swap, outside the box to drop; while dragging, equipment slots it fits light up. The line along the bottom names what's under the mouse. The editor closes it.
  - **Chests** (`StorageObjects`): any object kind with a `storage` setting (objects.js, `{ label, slots, columns }` over `STORAGE_DEFAULTS`; `objects/chest.json`, one in the hut). `TileMap.addObject()` gives each placed one its own `Inventory` (`obj.inventory`), which is progress like drops: never in the map file, empty after reload. E within `WARP_REACH` of any of its tiles (after NPCs and E warps, before E sound blocks, `INTERACTABLES`) calls `InventoryScreen.show(true, obj)`, which builds its box (group `storage`) above yours and moves yours down so both are centred; closing removes it. `InventoryScreen.dragging` is the `ItemSlot` dragged from, so drags work across both (`swapWith()`, and `Drops.drop()` takes the inventory). While open, `InventoryScreen.storage` is the object, for a future lid picture or animation in `drawObjects()`. New storage behaviour is a `STORAGE_DEFAULTS` line read in `StorageObjects` or `Inventory.fits()`.
  - **Worn things** draw on whoever wears them (`drawCharacter()` in character.js, used by the map and every preview): a band in their colour over the head, body, legs or feet (`WORN_BANDS`), accessories as gems down the side, until there are sprites. Characters say what they wear with `worn()`: the player from its equipment slots, an enemy from its spawn's `wears` (picked in the editor). Armour does nothing yet. Speedy Shoes (`wear: feet`) are the only wearable item.
  - **Q** drops the held item, thrown about `DROP_DISTANCE` towards the aim with some spread (`DROP_SPREAD`). It tries a few random spots, keeping the first `DROP_GAP` clear of other items, and moves with map collision so it stops at walls. Each map keeps its own in `map.drops` (progress, like `map.characters`).
  - A drop can't be picked up until the player has left `PICKUP_RANGE`, so it isn't grabbed straight back and "inventory full" shows once per approach, not every frame.
  - Each item has a `category` (`ITEM_CATEGORIES`, items.js: weapon, armour, item; only decides its editor tab) and a `rarity` (`RARITIES`), which sets its glow on the ground, mid-throw, in slots and the palette, and the colour of the held item's name above the hotbar. The glow (`itemglow.js`, everything goes through `drawGlowingItem()`) is a pulsing halo in the rarity colour plus `sparkles` pixel twinkles; a rarity's `image` replaces the drawn halo with a picture, and `ITEM_GLOW` holds the shared timings. Both lists are placeholders; a new line adds one. Rarity is per item type for now.
  - Items (with their weapons inside) load from `items/` alongside tiles, so there are none until then: `PLAYER.startingItems` are given after (`giveStartingItems()`), and the editor's item tabs read `ITEMS_BY_CATEGORY`, which fills as they load. If the files fail, there are none (console warning) and the player can't attack.
- **Sound** (`sound.js`, `soundblocks.js`, `soundeditor.js`). **The header of `sound.js` is the full guide:** the pieces, what happens when a sound plays, the synthesiser sample by sample, voices and talking, seamless loops, distance and doppler, known problems and ideas. `soundblocks.js` and `soundeditor.js` have their own. In short:
  - **The library:** every sound is plain settings kept by name in `SOUNDS` (sound blocks and everything else) or `VOICES` (npcs), from `sounds/` and `voices/`; a name is unique across both (`findSound()`). Audio files go in `sounds/files/`. They load before the maps, since sound blocks name their sound.
  - **The synthesiser:** `renderSound()` works out every sample in JavaScript (the old sfxr idea), seeded so a sound is the same every play. It's one synthesiser for everything, birds to engines to voices. Each `SOUND_SETTINGS` line is a setting and its slider at once. `renderSpeech()` says text in a voice a syllable at a time, and dialogue types at the voice's `talkSpeed`.
  - **Playing:** `playSound(name or settings, { x, y, map }, key, { loop, pitch, say })`, quieter with distance from the player's feet, panned, and bent by the doppler effect when things move (`Sound.update()`, every frame from sketch.js, which also stops loops you can't hear). `null` for the place is full volume. Opening the editor stops everything. Sound only comes out of this computer, so it doesn't affect multiplayer.
  - **Sound blocks** (`map.sounds`, each `{ sound, col, row, activate }`): tiles that play a sound on `step`, `interact` (E, a line in `INTERACTABLES`) or `loop`. `SoundBlocks.checkStep()` must run before `Warps.checkStep()`, since they share `player.stepTile`. A block naming a missing sound is kept but silent, and red in the editor.
  - **The sound editor** (`soundeditor.js`): a full screen synthesiser that `Editor.update()` hands control to, with a slider per setting, "make one" buttons (`SOUND_GENERATORS`), a piano, undo, and Export. It edits a copy (`SoundEditor.draft`) until Save.
- **Particles** (`particles.js`, `particleeditor.js`; the header of `particles.js` is the guide): bits that burst out, fly, fall onto the floor and fade. Each effect is plain settings from `particles/` (one `PARTICLE_SETTINGS` line per setting, also its editor row), kept in `PARTICLE_EFFECTS`. Top down: a floor spot plus a height, floor ones drawn under everything and flying ones sorted in with the characters (sketch.js). `Particles.burst(effect, x, y, { height, angle, img })`, emptied on changing map. A hit bursts the target's `hitParticles` and a dying enemy its `deathParticles` (each enemy spawn can pick its own). Only for show, so they'd stay on each computer in multiplayer, like sound.
  - **Nonstop:** tile and object kinds with a `particles` list keep bursting them (`ParticleEmitters`, whose comment explains the speed-ups), only on screen, capped at `PARTICLE_EMITTERS.share` of the limit and turned down on slow computers, so hits and deaths always show.
  - **Drawing is built for thousands:** one colour set per bucket of particles, `fillRect()` where it can, and flying ones drawn in runs between the characters. The comment above `ParticleSystem.beginDrawing()` has the measurements and what was tried first. Capped at `PARTICLE_LIMIT` (8000) per system, oldest first.
- **Atmospheres** (`atmosphere.js`, whose header is the guide; editor guide in the maps README): a map's look and feel over its tiles, picked by name (`map.atmosphere`) so a world's maps share one. One file each in `atmospheres/` (one `ATMOSPHERE_SETTINGS` line per setting, also its editor row and tab), kept in `ATMOSPHERES`; the 13 starters are one per kind of world.
  - **Drawn** by `Atmosphere.draw()` (sketch.js) after the things on the map and before damage numbers and prompts: two noise sheets (Fog and Overlay), a tint, drained colour, edges and lightning. It costs the same at any screen size (small tiled canvases stretched once, about 0.1 ms a frame). **Weather** is particle effects from `ParticleEmitters`, and the background **sound** loops from the map. Only for show.
  - **Areas** (`map.areas`): a box or oval of tiles with its own atmosphere on top of the map's (graveyard fog, lava heat). `areaAmount(area, x, y)` is the one rule its look, weather, edges and sound all go by. Editor: Triggers tab **area**, right click inside to edit.
  - **Editor** (`AtmosphereEditor`, toolbar **Atmosphere**): edits a draft shown live (`Atmosphere.preview`); **Save and export** also exports.
- **Shaders** (`shaders.js`, whose header is the full guide: the frame order, adding one, every helper, the sun, debugging): WebGL 2 effects over the world, dev mode only for now (**[ ]** go through `SHADERS`). After `gameCamera.end()`, `Shaders.apply()` runs one fragment shader over what was drawn, so the UI is untouched and no shader costs nothing. A `SHADERS` entry is `{ name, label, note, glsl }` with a `vec3 effect()`, given the `SHADER_COMMON` helpers (positions, the player, `lighting()`, `seen()`, `wallAtWorld()`, `thingAt()`). What casts shadows comes from `Shaders.casters()` and what glows from `Shaders.lights()`, so a new kind of thing that should cast or glow needs a line there. Shaders are checked by hand in a browser; the console says why one doesn't compile.
- **UI** (`ui.js`, `button.js`, `textfield.js`, `formbox.js`):
  - Everything extends `UIElement`. Groups show, hide and remove together. A click on UI is claimed, so gameplay never sees it. Elements draw in the order they were added, so anything that spills outside its element (a tip with a name in) goes through `UI.drawOnTop(fn)`, drawn after every element, or a later element covers it.
  - `FloatingWindow` (ui.js) is a window dragged by its title bar with an **×**: subclasses call `updateWindow()` and `drawWindow()` first. `ListWindow` is one with a scrolling list of clickable lines (the editor's problems, art report and keys). `ColourPicker` is one too.
  - Input only listens to keys in `KEYS` (`Input.gameKeys`, rebuilt by `Input.rebuildKeys()` after the pause menu changes one). `Input.shift`/`alt`/`ctrl` follow the last event; `Input.wasPressedWithShift(action)` is the reliable way to tell Ctrl + Shift + Z from Ctrl + Z. `Input.captureNextKey(fn)` hands the next key press to `fn` (the pause menu's key changing).
  - `Input.typing = true` routes keys to `Input.typed` instead of the game. The box's owner picks the focused `TextField`/`NumberField` and calls `field.type(key)` per key; Ctrl + V arrives as `{ paste: text }` → `field.paste(text)`. While typing, Ctrl + V/C/X/A are left to the browser and every other Ctrl combo but dev mode's is ignored, so the editor's shortcuts never fire mid-typing. The arrows type as `'ArrowUp'`/`'ArrowDown'` (a `NumberField` nudges by 1), and with Shift, Tab and the arrows come as `'Shift+Tab'` etc. (back a field, nudge by 10). Clicking a `Slider`'s number types an exact one (`Slider.typing`), and it uses up `Input.typed` so its Enter and Escape don't reach the box. `ColourField` accepts pasted hex or rgb, and its swatch opens `ColourPicker`, a small window dragged by its title bar, separate from the form box, which reopens where it was left (`ColourPicker.spot`): a saturation/value square (drawn pixel by pixel, since stacked canvas gradients leave a diagonal seam on some GPUs), a hue strip, sliders for one of `COLOUR_MODES` (RGB, HSB, HSL, CMYK; a mode is `channels`, `from(hsv)` and `to(values, hsv)`), old/new swatches, recent colours and the browser's `EyeDropper` where there is one. Mode and recent colours are in localStorage (`sq-colour-picker`).
- **Editor** (`editor.js`, `editormenu.js`, `edittools.js`, `edithistory.js`, `mapcheck.js`):
  - Game-engine layout: `EditorMenuBar` on top (File, Edit, View, Map, Tools, Help; **Play** and **Play here** in the middle; the map's name, size and an unsaved dot on the right), `EditorToolStrip` down the left (tools, brush, undo, redo), `EditorDock` on the right (palette tabs, `PaletteSearch`, `RecentStrip`, `PaletteGrid`, inspector), `EditorStatusBar` at the bottom. Sizes in `EDITOR_LAYOUT` (`toolbarHeight` is the menu bar), colours in `EDITOR_COLOURS`, buttons use the compact `editor`/`editorPrimary` `BUTTON_STYLES`.
  - **Commands** (`EDITOR_COMMANDS` in editormenu.js) are everything a menu or key does: label, `key` (a `KEYS` action the editor checks), `devKey` (one dev mode already checks, only shown), `enabled()`, `ticked()`. `EDITOR_MENUS` lists them per menu. `EditorKeys.update()` runs a command's key while nothing's being typed and no mouse button is held (Shift turns undo into redo and save into save as), closing any open menu first. After it, `Editor.update()` stops for the frame if a key closed the editor or opened a box: carrying on is what left the Edit button showing after Play here. The inspector's buttons work out whether they're there each frame (`EditorButton`'s `shows()`), so nothing sets their `visible`; only the group's show and hide do. `Editor.choose(thing)` is the one way to pick from somewhere else (the map, the recent row, the art report): it picks, opens the tab, scrolls to it and swaps a tool that can't use it for Paint. An open menu is its own element (`EditorMenuList`), moved last in `UI.elements` so it's on top and covers the screen; the click that opens it is ignored by it (`openedOn`).
  - **Tools** (`EDITOR_TOOLS`, `EditTools` in edittools.js): `Editor.tool` is paint, erase, fill, rect, select or pick, and `Editor.selected` is always what's picked (Erase is a tool now, not `selected = null`). `EditTools.update()` does the left button; Alt + click picks with any tool, Shift + drag is a rectangle for Paint (tiles) and Erase. `Editor.brush` (1 to `EDIT_TOOLS.maxBrush`) sizes Paint and Erase. A press counts as held for its first frame, so a click that's let go within a frame still paints. Copy and paste: `EditTools.selection` and `clipboard` (tiles, overlapping objects, characters, warps, sound blocks, areas inside, positions relative to the box); stamping skips empty tiles, renames warps that clash and replaces warps and sound blocks on the same tile.
  - **Undo** (edithistory.js) compares the map's design (`designOf()`, `designKey()`) after anything that might change it (a release, key, box closing, or every `EDIT_HISTORY.checkEvery` s) and pushes the old one if it differs, so nothing has to report changes. Per map (`WeakMap`), until reload. Chests keep their `Inventory` through undo. Restoring copies the design again, resolves renamed tiles and respawns characters. Not covered: catalogue settings (tiles, sounds, items), which have their own boxes.
  - **Saving**: the file text (`mapFileText()`) is compared with what it loaded or was last saved as; while different the map is unsaved and a copy is kept in localStorage (`MAP_DRAFT_PREFIX` + name). Opening a map in the editor never throws a copy from before away (only changing or saving it does). **Save** (Ctrl + S) exports under the map's name if it's in `DataFiles.listed.map`, otherwise **Save as**. **File > Recover unsaved changes** (`openRecoverBox()`) brings one back via `registerMap()` + `loadMap()`, keeping the file's text as what counts as saved. Closing the page only warns if a copy couldn't be kept (`EditHistory.notKept`).
  - **Palette search** filters `PaletteGrid.names()` by name or label; it takes `Input.typing` while focused and lets go when a box opens. The **recent row** (`Editor.recent`, localStorage `sq-editor-recent`) is filled by `Editor.pick()` (not `checkSelected()`); Shift + click pins.
  - **Map menu**: **World map** (warpgraph.js), **Find uses** (`findUses()`, mapcheck.js: tiles counted per map, anything placed whose settings name the picked thing, and catalogue entries that name it, through `mentions()`, which only looks inside plain objects and lists), **Check for problems** and **Check every map** (`mapProblems()`, mapcheck.js) and **Art report** (`ART_PROBLEMS` from `artProblem()` in utils.js as pictures fail to load, plus `artSizeProblems()`); both `ListWindow`s in the `'editor'` group. `Editor.goTo()` moves the view and flashes a tile, and `Editor.goToMap()` loads another map first.
  - **Minimap** (`EditorMinimap`, editor.js, View > Minimap): one pixel per tile from each tile's colour, made again every `MINIMAP.redrawEvery` s (a `ponytail:` note says how to only redraw on changes), plus warps, spawn, characters and the view box; click or drag moves `Editor.view`.
  - **Enemy senses**: resting the mouse on an enemy spawn draws `ENEMY_SENSE_RINGS` (its `ENEMY_SPAWN_STATS` ranges, labelled) round its feet, and lights the floor it can see (`clearLine()`) and darkens what walls hide (`drawEnemySenses()`).
  - **Play here**: Space with the mouse on the map plays from there; Space anywhere else, **Help > Play here** and the button wait for a click on the map (`Editor.startPlayHere()`, decided by `UI.hovered` this frame, since `Editor.over` is last frame's). Esc or right click stops waiting. It closes the editor and places the player on that tile (then `Warps.arrived()`). Closing remembers the view (`Editor.lastView`), and opening on the same map goes back to it. **Tab** hides the editor (`Editor.uiHidden`).
  - Palette tabs are for placeable things only; whole-map actions are in the menus. `EditorTabStrip` draws tabs at natural width and scrolls (wheel, or **‹ ›** when they overflow), so `EDITOR_TABS` can grow. **Lights** is an empty example.
  - **Weapons** and **Items** get a tab per `ITEM_CATEGORIES` entry. Clicking the map drops one (`Drops.place()`; progress, not saved by Export). **Give** adds one to the inventory; **Edit** (or right click in the palette) changes name, rarity, colour and everything about its weapon (weaponeditor.js) immediately. The Weapons tab ends with the enemies' own weapons, which any click opens. **Export** on those tabs downloads the files of changed items (`itemToData()`, weapon inside) for `assets/squimble-quest/items/`, and of enemies whose weapon changed. Adding, renaming or deleting is by hand (the file and `index.json`).
  - Clicking the map with Paint and something picked runs its tab's `place()` (`EDITOR_TABS`); tiles have none, since they paint while held.
  - **Triggers** (spawn and warps, `TRIGGER_TYPES`) make things happen. Not a catalogue: each has its own `place()` there. Placing a warp opens its settings.
  - **Right click** opens settings for what's under the mouse (`editWarp()`, `SoundBlocks.edit()`, `editEnemy()`, `editNpc()`); future settings hook in at the same spot in `Editor.update()`. The enemy box has tabs (**Gear** first: a `holdPicker()` saved as the spawn's `holds`, and one `wearPicker()` per `EQUIPMENT_SLOTS` entry saved as its `wears`; then **Stats**, **Behaviour** and **Effects**; the sliders on Stats and Behaviour are its `ENEMY_SPAWN_STATS` (enemies.js: health, speed, damage and attack rate multipliers, knockback and stagger taken, sight, hearing, chase range, memory, alert range, attack range), saved as the spawn's `stats` only where they differ from its kind's, which the bar marks (`rowSlider()`, `Slider.showNormal`); right click or **Reset** goes back. `Enemy` lays them over its kind, so everything reading `enemy.type` gets them), and it and the NPC box show a `CharacterPreview` (inventory.js) down the `side`. Every row in these boxes and the item box has a `tip`.
  - **Erase** is a tool (as are Select + Delete and Cut). Right click never deletes.
  - `FormBox` (formbox.js, with `Picker`, `MultiPicker`, `Checkbox` and `Slider`) is the in-game ask box: New/Resize sizes, New's fill, Save as's name, warp, enemy, tile and particle settings, the pause menu. A box with tabs opens on the tab it was last on (`FormBox.lastTabs`, by `memory` or the title up to a colon). `cancelLabel: null` leaves Cancel out. `hint` can be a getter (it's read every frame). Give it a title and `rows` (or `tabs` of rows) and it lays out; `side` adds a column beside the rows (the tile editor's pictures). A row's optional `tip` shows under it while the mouse rests there (`FormBoxTip`). `Picker` is choose-one: its ends step, its middle drops down a `ChoiceList` of every choice (`tilePicker()` in editor.js makes a tile one). `MultiPicker` is choose-several in one row, ticked in the same list, so a setting with lots of choices never spills onto extra tabs; use it rather than a column of `Checkbox`es. Only one list is open at once (`ChoiceList.current`); Escape, clicking elsewhere, switching tab or closing the box shuts it. Any UI element with a `value` can be a row field. It's a window: dragging the title moves the whole `form-box` group, **×** cancels. `onUpdate` runs every frame while open, `onCancel` on closing unconfirmed.
  - `PaletteGrid` is one element that draws and hit-tests every square, reading catalogues each frame, so new tiles appear automatically. It scrolls (clipped) and consumes `Input.wheel` while hovered, so the camera doesn't zoom. **Right click** a tile square for the tile editor. The inspector's **New** and **Export** show only on Tiles, **Edit** while a tile is picked.
  - While WASD pans, the editor UI and dev panels fade (`Editor.uiAlpha`, applied in `sketch.js`).
- **Screen size** (`config.js`, `fitResolution()` and `toggleFullscreen()` in sketch.js, the frame in squimble-quest.css): how big it's shown is separate from the game.
  - **Game px:** everything is laid out and played in 960 x 540 game px (`GAME_W` x `GAME_H`). Gameplay, UI and the camera only ever see these, so it plays the same at any size.
  - **On the page:** as big as fits, up to 1920 x 1080 page px: never wider than the window, no taller than the window minus the sticky header and the bar under the game, but never under the 960 it used to be (`--sq-game-w` on `.sq-game-frame`). It can be wider than the page's container, so it centres itself on the page. Clicking to play scrolls all of it into view if it's partly off screen (setup()).
  - **Sharpness:** the canvas draws at the resolution it's shown at (`fitResolution()`: its page width x `devicePixelRatio` over `GAME_W`, set with `pixelDensity()` whenever its size changes, capped at 4). Full screen on a 1080p monitor that's exactly 2, so it's the same game drawn at 1920 x 1080. Tiles (`drawTiles()`) and the camera (`pixelSnap()`) round to real screen pixels using `pixelDensity()`.
  - **Full screen:** **F** (`KEYS.fullscreen`) or the button in the bar under the game puts the frame full screen (`toggleFullscreen()`), with the game centred and black bars if the monitor isn't 16:9 (`.sq-game-frame:fullscreen`). A message says how to leave, cleared when it's left. The editor's boxes use Escape, so in Chrome and Edge it locks the keyboard's Escape (`navigator.keyboard.lock()`): a tap still reaches the game and holding it leaves full screen. Other browsers leave on a tap. The browser only allows full screen just after a key press or click.
- **Dev mode** (`debug.js`): info panel top left, sized to its text (long values cut with `fitText()`), hidden in the editor unless **View > Dev info panel** is ticked (`Debug.show.editorPanel`). The overlays (grid, AI routes, atmosphere), their keys and zoom also work in the editor without dev mode (`Debug.showing()`), for builders. **H** opens `DevMenu`, one `UIElement` that lays itself out each frame: ticks for `DEV_INFO` (panel readouts) and `DEV_OVERLAYS` (map overlays, read with `Debug.shows(name)`), buttons for `DEV_TOOLS`, and `EDITOR_KEYS` while the editor's open. Key chips come from `KEYS` via `keyName()`, so rebinding updates the menu. Ticks are saved in localStorage (`sq-dev-show`).

## Rules to keep when changing things

Not obvious from any one file; breaking them causes hard-to-trace bugs.

- **Change maps only with `loadMap(name, warpName)`.** It stores the old map's characters, restores or makes the new one's, places the player, calls `Warps.arrived()`, and sets up the camera. Setting `worldMap` directly skips all that.
- **Anything moving the player without walking must call `Warps.arrived(player, worldMap)` after** (teleports, cutscenes, being carried or pushed), or a step warp under them fires. `loadMap` and `Player.respawn` already do. Dev mode's **T** deliberately doesn't, to test warps.
- **The live characters are the globals `enemies` and `npcs`.** `map.characters` is current only for maps the player *isn't* on (written on leaving). Other maps: read `map.characters`. Current map: the globals.
- **One map, one name.** `getMap()` names a map when building it; only Export renames it (the old name reverts to its file). Never let two `VISITED_MAPS` names point at one map. Warps, dev mode's **M** and Export all use `map.name`.
- **Design and progress are separate.** Tiles, objects, spawn lists, warps and `spawn` are design (what Export saves). Progress (`map.characters`, `map.drops`, player health and inventory) is memory only; a save system would store it beside the map files, not in them.
- **The editor always shows the design.** Opening, closing or changing characters runs `spawnCharacters()`, resetting the current map's enemies and NPCs. Keep it so, or the editor would show a half-played map as the design.
- **A map's name is its file name,** and warps target maps by name. Renaming a map file breaks every warp to it (red in the editor, listed in the console).

## Ideas for later

Only build these when needed.

- **Combat:** enemies dodge rolling (wearing the quick charm, given in the editor, plus an ai that sets `roll` in its controls); enemies winding up before they swing (a flash or a pause, so you can react; now they hit the instant they're in range); a hit interrupting a swing in progress; a screen shake setting in the game's options for people who don't like it (one multiplier in `hitWith()`); particles in the weapon preview (it'd need its own `ParticleSystem`, like `ParticlePreview`); a hit sound per combo hit (a hand-written `hitSound` in a combo hit works in the game, but the editor's Save drops it, like colour).
- **Warps:** objects that are warps (a door/trapdoor/manhole object opening its warp, see the end of the Warps notes); a "back where you came from" target for shared interiors; a fade between maps; locked doors; an editor key to go through the warp under the mouse.
- **Sound:** sounds for things that happen (sword swings, footsteps as a tile setting, doors on warps, enemies hurt or dying, ui clicks), all just `playSound()` calls; a little random pitch per play so footsteps vary; sounds that follow a moving enemy; walls muffling sounds (`clearLine()`); music; a volume setting or mute key; more effects (reverb, distortion, chorus); chords; consonants and emotions when talking; drawing your own wave; renaming and deleting sounds in the editor; step blocks enemies set off; a cooldown or "only once" step blocks. The full list with how to start each is at the end of the `sound.js` header.
- **Particles:** single emitter blocks placed on the map like sound blocks (now only tile and object kinds make them nonstop); particles on more events (footsteps as a tile setting, items breaking, warps); a spawn area shape (a line or the whole screen, for weather over a map rather than per tile); walls with a height so bits fly over low ones (the `ponytail:` note in `ParticleSystem.update()`); renaming and deleting effects in the editor.
- **Particles:** if thousands more are ever needed (or big glowing shapes in their hundreds), draw them on a WebGL canvas the way `shaders.js` does, a few calls a frame however many there are, copied onto the game canvas once per run between characters. Measured first: shapes other than squares and small circles cost the most now.
- **Atmospheres:** wobble (underwater, heat haze) needs pixels moved, so the shader pipeline running for real; an atmosphere setting the shaders' sun and darkness so caves and space are dark and torches matter; areas that move (a storm cloud drifting over) or are painted tile by tile; renaming and deleting them in the editor; more than two sheets if two runs out.
- **Shaders:** turning one on for real (a map setting like `"look": "shadows"`, not dev mode only); stacking passes (lighting then bloom, needs framebuffers in `Shaders.apply()`); placed lights from the editor's empty **Lights** tab, and a `light` setting on tile and object kinds (torches, lava), fed into `Shaders.lights()`; soft shadows; objects with a height blocking light and casting sun shadows; the sun as the real time of day (with night, and the torches coming on); upright buildings that cast like characters, and gameplay that reacts to light (vampires in sunlight, spawning in the dark), both planned out under "experimental, and plans for later" atop `shaders.js` (gameplay must never read shader output; the game works out light itself and the shader only draws it).
- **Items:**
  - stacking (arrows, potions), needing a count per item
  - editor-placed items aren't saved in the map file; that needs a list in the file like `spawns`, and a decision on whether picked-up ones return. The same goes for what starts in a chest (an `items` list on its object entry in the map)
  - chests: shift click to move an item straight across, chest art and a lid opening (`InventoryScreen.storage`, see Inventory), storage that only takes some items (a quiver) or locks
  - making new weapons and items in the editor, like the tile editor's **New** (now by copying a file in `items/`); the same for enemies, NPCs and objects, which have no editor box yet
  - Speedy Shoes, and armour in general, do nothing yet: a defence or speed setting on items, read through `worn()`
  - bows don't use up arrows (that needs stacking first), and arrows are a drawn line until there's a sprite
- **Multiplayer, maybe.** Not decided. The idea: a small social game for friends, up to about a classroom (20–40), playtesting and hanging out, never hundreds. Every spot in the code that'd need changing is marked with a `multiplayer:` comment; search for it. If it happens:
  - **Helps already:** every character runs on `{ move, aim, attack }`, so another player is a `Player` with networked controls. `world.players` is a list, AIs use `nearestPlayer()`, enemies hit every player, step warp tracking is per player, and nothing in gameplay pauses the world. Maps and tiles are data a server can load. Progress is separate from design. The only randomness (drop spots) goes through `randomBetween()` in utils.js.
  - **In the way:** one running map is assumed (globals `player`, `worldMap`, `enemies`, `npcs`, and `loadMap()` swapping the whole world). Players on different maps need each occupied map running, so maps become "rooms" each holding their own characters and players; that also decides how `Warps.followers` (enemies in transit between maps) and `Player.respawn()` (reads the global `worldMap`) work. A drop's `ready` flag is shared, so one player walking away readies it for everyone, including the one who dropped it (it needs to remember who dropped it). `setTile()` still calls p5 (`color()`, `loadImage()`), so rules and drawing need separating for a server. Dialogue, the hotbar, `Interact.target` and the editor are the local player's UI, which is fine as each client has its own. Who may open the editor and dev mode is already a role (`ROLES`, `player.can()`), which the server would set per player and check again on anything they send. Also marked:
    - the pause menu, Auto pause and the editor stop the whole world (`paused` in sketch.js); with others there they'd only be a menu
    - the hit stop (`Character.freeze()`) only freezes the two characters, but with lag your computer hears about a hit after you've moved on, so it'd snap you back unless the hit is guessed locally first. `hitWith()` does the rules and the show together and would split in two
    - the hotbar, inventory drags, Q, chests and E change the game straight from input in sketch.js and inventory.js, not through the controls, so they'd become actions sent with them. Items have no ids to name in those actions (`createItem()`)
    - `randomBetween()` is mostly used for show, so a shared seeded one would drift apart; it'd split into a rules one and a show one
    - `MAX_DT` (config.js) makes slow computers play in slow motion and hidden tabs don't run at all, so the server would tick the rules itself
  - **Needs a small server** at that size (Node + WebSockets, cheap to host), not a player's browser hosting: the host's upload or a throttled hidden tab would stall everyone, and school networks often block browser-to-browser connections. The server runs the rules without p5, so rules and drawing need separating first. Each player only needs updates for their map.
  - **Social layer:** names over heads, chat (filtered if younger players might join), emotes, hangout maps sized for a crowd.

## Known issues and loose ends

- **Open file uses the browser's file picker,** which must stay (only the browser can read local files). Failures show via `showMessage()`, with the reason in the console.
- **NPCs can be hurt by tiles.** At 0 health an NPC is marked `dead` but keeps standing: still talkable, others walk through it. Nothing places NPCs on damage tiles yet. When NPCs can die properly, handle it in `Npc` (npc.js), like `Enemy.die()`.
- **Enemy AI loose ends** (pathfinding.js):
  - In a one-tile corridor only the front one can fight; the rest wait behind or go round if there's another way. Fine for now.
  - When every tile round the player is taken, extra enemies find every way through the crowd too costly, their search runs out and they wait where they are with "(no way)" until a spot frees.
  - The full list is under "known limits" atop pathfinding.js.
  - Push and slippery tiles aren't in their plans (see the `ponytail:` note atop pathfinding.js).
  - Sight ignores objects (furniture is low). A tall object that blocks the view would need a setting.
  - `direct` enemies get the new senses (sight, memory) but still walk straight into walls, on purpose.
- **Sound loose ends** (full list in the headers of `sound.js`, `soundblocks.js` and `soundeditor.js`):
  - If a loop block is in range when the page loads, Chrome logs "The AudioContext was not allowed to start" and it stays silent until the game is clicked. Harmless.
  - Changing a `normal` value in `SOUND_SETTINGS` changes every sound that left that setting out of its file (most of them), since only non-default settings are saved. Renaming a setting's `key` or a wave loses it from every saved sound.
  - Step blocks have no cooldown (walking back and forth plays them over and over), and only the player sets them off.
  - Two loop blocks with the same sound nearby play it twice, louder, drifting in and out of step.
  - In the sound editor: the saved name is the cleaned up one ("My Sound" becomes `my-sound`, shown next to the box), and with Loop on each change restarts the sound with a tiny blip. Long sounds (the nature loops) can stutter while dragging a slider, since the picture works the sound out every frame.
  - Smaller sound quirks: punch can click after a long fade in, the noises stop getting brighter above about 1400 Hz, a filter swept fully off and back on can pop, loud resonance/flanger/echo gets clipped, loops repeat their random parts exactly and don't carry echoes over the join, talking guesses syllables from spelling, an npc's first line can take a frame to work out, and a failed audio file isn't retried until reload.
- **Combat loose ends** (weapons.js, character.js, weaponeditor.js):
  - Enemy archers draw while `canAttack()` holds; if you step out of range mid-draw they let go early with a weak shot.
  - Saving in the weapon editor rewrites `combo` from `HIT_SETTINGS` only, so a combo hit's own `colour` or `attack` written by hand is dropped (`hitsToSettings()`).
  - Exporting an enemy from the Weapons tab rewrites its whole file from `ENEMY_DEFAULTS` order and drops values equal to the default (the grunt's `width: 28`). Same game, different text.
  - Only an enemy kind's weapon has an editor. Its stats are edited per spawn (saved in the map); a kind's own stats are still its file.
  - The weapon preview uses the kind's or `PLAYER`'s settings, not a spawn's stats, has no particles and a flat floor with no walls (`PREVIEW_FLOOR`).
  - Knockback and recoil lock walking until they slow to `COMBAT.pushLockEnd`; the last few px after that can be walked against.
  - Knockback can shove an enemy into lava: pushes aren't in the pathfinder's plans (its `ponytail:` note).
  - Fear (pathfinding.js) only grows with damage; a hurt enemy below `PATH_SAFETY` of its health refuses all harm but still chases over safe tiles. (It used to stop dead at 10% health saying "(no way)": the safety check ran on harmless steps too. `tests/pathfinding-check.js` covers it.)
- **Dying is a placeholder** (`deathscreen.js`): you disappear, the screen says "You died", and Respawn brings you back with full health and nothing else lost. Its header lists ideas to try (losing items, a timer, a killed-by line). Editor **Play here** doesn't revive a dead player; Respawn still does.
- **Respawn location is undecided.** Currently the spawn of the map you died on (die in the hut, respawn in the hut). Options: always the game's start, the last warp you came in by (the old way), or checkpoints. It's all in `Player.respawn()` (player.js), marked `ponytail:` with notes on each option, so only that function changes.
- **Map progress lasts until reload.** No saving yet. That includes what's in chests, and erasing a chest in the editor loses what's in it.
- **Renaming a warp breaks warps to it.** They keep the old name, show red in the editor, and the console lists them on load.
- **Nothing stops a warp or the spawn ending up on a solid or empty tile** (painting a wall over it, erasing under it), which traps the player. The editor's **Map > Check for problems** lists them, but doesn't prevent them.
- **Placeholder art:** coloured rectangles until sprites exist. A character's rectangle is its hitbox (`width`/`height`, `bodyBox()`, drawn by `drawBody()`) , a swing's swoosh is its real reach and arc (`MeleeSwing.draw()`) and a jab's band is its real reach and width (`Jab.draw()`). Nothing in the game reads what's drawn, so sprites can be any size, and those two can move behind a dev overlay (both marked `ponytail:`). Every catalogue and `PLAYER` already has an `image` setting (`texture` for tiles), and `PLAYER` a `deathImage`. Grass has a test dual grid tileset (`assets/squimble-quest/tiles/dual-grid/grass_tileset.png`).
- **Dual grid tiles have no variants or frames** (normal tiles do). It'd need a tileset per variant, picked per corner in `drawDualCorner()`.
- **The tile editor can't reorder tiles.** Do it in `tiles/index.json`. Renamed and deleted tiles stay in `oldNames` for good, so a name once used can map to a tile you didn't expect if it's reused for a new tile (the new tile wins, since `resolveTileName()` checks real names first).
- **Undo is only for the map,** not tiles', sounds' or items' own settings (their boxes have Cancel). It lasts until the page reloads.
- **Editor keys while typing:** the palette search and every box take the typing, so tool keys and Ctrl shortcuts (apart from Ctrl + D) wait until they let go.
- **Screen size quirks** (see **Screen size** under [How it fits together](#how-it-fits-together)): when the game isn't shown a whole number of times 960 wide (most window sizes on the page, or full screen on a 1366 x 768 or 1440p screen), pixel art gets uneven pixels (below), and lines and text land between pixels; full screen on 1080p (2x) and 4K (4x) is exact. 4K is a lot to draw each frame; not measured on a real one.
- **Pixel art at in-between zooms:** art is unblurred (`noSmooth()` in `sketch.js`), so at e.g. 1.35 some art pixels are a screen pixel wider. Normal for non-integer pixel art scaling; there are no gaps or lines between tiles.

## Checking changes

- **`node js/squimble-quest/tests/run.js`** runs every check in `tests/` and says which failed (`run.js sound` runs just the ones with "sound" in the name). Each check's header says what it covers; they're silent when they pass. Run it after any change, and `catalogue-check.js` and `data-check.js` especially after adding or exporting data files. `node --check <file>` catches syntax errors.
- New checks load game files with `load(files, fakes)` from `tests/load.js` (or `loadFighting()` for characters and weapons, with `FLAT_FLOOR` to fight on), which hands back every global, so a check is mostly its asserts.
- Real behaviour: play it in the browser. To automate, install `playwright-core` in a scratch folder, launch Chrome through it (`executablePath`), serve the site, then click and type into the canvas. Globals (`worldMap`, `enemies`, `Editor`, `loadMap`, ...) are readable via `page.evaluate`. Notes:
  - the game is 960 x 540 game px whatever size it's shown at; compute clicks from the canvas's bounding box
  - the first canvas click only focuses it
  - use `page.keyboard.down/up` for held keys
- For behaviour-preserving refactors, compare before and after: in `page.evaluate`, call `noLoop()`, then call `draw()` yourself with `window.deltaTime = 1000 / 60` and `Input.held` set to the keys you want, recording positions, health and a canvas pixel hash at checkpoints. Pin `window.frameRate = () => 60` first or the dev panel's fps makes frames differ. `mapsReady`, `worldMap` and other `let` globals aren't on `window`; read them by name.
  - **Set `window.deltaTime = 1000 / 60` before every `draw()`, not once.** p5's own frame that was already queued when you called `noLoop()` overwrites it with a big gap (capped to `MAX_DT`, 0.05 s), so timers run 3× fast and things like combos time out between hits.
- Combat checks that worked: put a dummy (`new Enemy('dummy', ...)`, knockbackTaken 0) or a grunt (`new Enemy('grunt', col, row, 'still')`) beside the player in `enemies`, pick a weapon with `player.inventory.selected = n`, then step frames calling `player.update({ move, aim, attack, charge }, 1 / 60, world)` directly (world as in `draw()`) and read `health`, `x`, `comboStep`, `charge`, `pushVelocity`, `frozen` and `gameCamera.shaking`. For the editor: `Editor.open(player, gameCamera)`, `Editor.editItem('sword')` or `Editor.editEnemy(spawn)`, then set a row's `field.value`, `FormBox.update()` and `FormBox.confirm()`; the preview is `UI.group('form-box').find((e) => e instanceof WeaponPreview)`.
